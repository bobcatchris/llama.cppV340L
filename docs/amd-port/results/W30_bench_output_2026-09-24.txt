Q: why is the C4 fused arm (GGML_CUDA_MMVQ_GLU_FUSION_T4, mul_mat_vec_q
<type, ncols_dst=4, has_fusion=true>) oracle BIT-EXACT on iq3_s but FAIL on
iq4_xs (19449/69632 els, max_rel 0.114, broad over all tokens / both row
parities / all CTA buckets)?

A: FMA-contraction divergence between template instantiations. NOT a logic
bug. The fused branch is semantically identical to the served pair sequence
(same vec_dot_q_cuda, same geometry, same dst layout; up dot at
ggml/src/ggml-cuda/mmvq.cu:782-783, gate dot at mmvq.cu:786-788, silu
epilogue at mmvq.cu:841-870 vs bench glu_apply_swiglu at
docs/amd-port/tests/bench_mmvq_real.cu:149-156). Both vec_dots end in the
same float skeleton,

  acc += (float(bq.d) * float(bq8_1.ds)) * float(sumi)
  [vecdotq.cuh:1660-1661 (iq4_xs), vecdotq.cuh:1483-1484 (iq3_s)]

which contains one contractible a+b*c site per accumulation step. Under the
HIP default -ffp-contract=fast the compiler is free to fuse it per
instantiation, and it fused inconsistently:

ISA evidence (hipcc -O3 -x hip --offload-arch=gfx900 --save-temps on
bench_mmvq_real.cu at the W30 build flags; kernel bodies extracted from
bench_mmvq_real-hip-amdgcn-amd-amdhsa-gfx900.s):

  kernel              v_fma_f32  v_add_f32  v_mul_f32   accumulation in the
                                                                   hot loop
  iq4_xs pair  (T4)      1          63         30      7/8 chains mul+add,
                                                         1/8 chain fma
  iq4_xs fused (T4)    115         156         92      all chains fma
  iq3_s pair  (T4)      16          56         16      fma
  iq3_s fused (T4)     115         156         92      fma

iq4_xs pair loop-carried merges (block %.loopexit165): seven v_add_f32
acc-merges plus exactly one v_fma_f32 (v9); the per-dot tail is
v_cvt_f32_f16, v_cvt_f32_i32, v_mul_f32 (d*ds), v_mul_f32 (t*sumi) ->
3 roundings per step. iq4_xs fused tail: v_cvt_f32_f16, v_cvt_f32_i32,
v_mul_f32 (d*ds), v_fma_f32 (t*sumi+acc) -> 2 roundings per step. That
rounding difference on every one of ~160 accumulation steps reproduces the
observed signature exactly: ulp-scale rel errors (sampled 1.5e-7..4.9e-7),
broad uniform mismatch (28%), max_rel 0.114 at near-cancellation outputs.
iq3_s pair and fused both chose fma -> same rounding -> BITEXACT. The
contraction choice flipped for iq4_xs because the fused instantiation
carries 16 accumulator chains (T=4 x rpb=2, up+gate) vs 8 and compiles
completely differently (OCC: fused iq4_xs 63 regs / 80B local / 8 ctas vs
pair 84 regs / 48B / 6 ctas); clang's contraction heuristic is
instantiation-local, so bit-exactness of a fused variant vs the pair
sequence is not guaranteed by the source and cannot be asserted per type
without the oracle - exactly why the oracle-first law exists.

CLASSIFICATION: numerics-class (candidate (a), fp-order/contraction), not
(b) pre/post-scale (epilogue applies silu AFTER the full gate dot and BEFORE
the up multiply on both paths), not (c) wrong index/missing scale (both dots
use the same kbx_offset/kqs/stride indexing as the pair launches; the oracle
reference is produced in-process from the same vx/vgate buffers, so offset
errors cannot produce this signature).

Owner-sign-off lever (accept ulp-level divergence): NOT APPLICABLE. The
lever is only worth pulling if the arm is faster. It is not: fused iq4_xs
2612.4 us vs pair 1211.2 (2.16x slower; recorded timing, oracle-defective
run) and fused iq3_s 4241.9 vs pair 3481.5 (+21.8%, exact). Signing off
numerics to keep a 2x regression is a non-starter.
