# W2 Cell Receipt: bench_mmvq_gfx900 (iq3_s 17408x5120) - 2026-09-21

Instrument: docs/amd-port/tests/bench_mmvq_gfx900.cu, standalone hipcc build,
run on die 3 (dev cell; serving world untouched). Weights = REAL tensor bytes
(blk.21.ffn_up, 38,297,600 B) H2D once; x = synthetic valid q8_1; 200-iter
hipEvent timing. Kernel = verbatim vec_dot_iq3_s math, schedule-cloned from
mul_mat_vec_q (GCN table, T=1).

VALIDATION: shipped-config clone = 105.2 GB/s effective vs census-derived
~101 GB/s (per-die slices of mixed shapes) -> cell is a valid relative
instrument. Byte floor at 183.8 GB/s (sequential-copy ceiling) = 208.8 us;
cell runs 364.7 us = 1.75x off that floor.

## Incidents (per the can-fail-before-can-green law)

1. First bench build mapped 28,200,960 B (a stale per-tensor byte figure
   from an earlier extraction script's buggy nbytes math) for a 38,297,600 B
   tensor -> out-of-bounds GPU reads -> memory fault on the rows variant.
   All numbers from the mistuned build are VOID. Root cause chain: the
   authoritative per-tensor size is next_offset - offset; any computed size
   must be checked against that. Layout itself is STANDARD GGML (validated
   all 866 tensors: offset deltas == standard type sizes).

## Named next link

The five schedule rungs all lost: the kernel is bound by neither slots,
occupancy (39-40 VGPR -> high residency), nor MLP. Remaining gap 105 ->
183.8 GB/s needs the access-pattern ceiling named first: a PURE-CONSUME
kernel (same 38.3 MB buffer, xor-consume, no decode) reports the real DRAM
wall for scattered 1,416-B block reads. If pure-consume lands ~105-110
GB/s, the shipped kernel is AT the pattern ceiling and the only doors are
layout-level (e.g. interleaved row-major re-pack at load time - weights
never change, so a load-time repack is free at steady state). If
pure-consume lands ~180, the decode chain (constant-LUT latency + dp4a
emulation) is exposed and the B-rungs (decode-atom rework, fp16x2
accumulate with acceptance pricing) are live.

## Addendum: pure-consume ablation (bench_consume_gfx900.cu) - the doors are named

| kernel                                   | us    | GB/s  | reading |
|------------------------------------------|-------|-------|---------|
| consume_seq (coalesced uint4)            | 117.0 | 327.5 | pure-read ceiling >> 183.8 copy figure (copy is half-read/half-write) |
| consume_pattern (exact MMVQ geometry, loads only) | 156.3 | 245.5 | access pattern NOT the wall |
| consume_pattern_lut (+8 constant LUT lookups, no decode ALU) | 216.1 | 177.6 | constant-LUT chain = -28% |
| gemv shipped (full decode + emulated dp4a) | 364.7 | 105.2 | decode+dp4a chain = further -41% |

Additional negatives: manual ILP2 unroll (NW2 79.4 / NW4 101.1 GB/s) - the
chain is per-lane serial and does not overlap by unrolling; LDS-LUT already
banked negative. Multi-rows/MLP banked negative earlier.

CONCLUSION: the shipped MMVQ sits at 105 GB/s; the pattern itself can carry
245 GB/s. The residual lives in the per-lane dependent decode chain:
constant-memory LUT lookups (-28%) then decode arithmetic (-41%). Schedule
levers are exhausted (7 banked negatives). The live doors are decode-atom
redesign (perm/LUT-free or fp16x2-packed atoms - fp16 changes numerics ->
acceptance-priced via the canary; integer atoms bit-exact) with a realistic
first target of 130-150 GB/s (= +25-40% decode kernel = +19-31% served
decode), and secondarily the LUT-access pattern (8 divergent constant reads
per 32 weights).

## ADDENDUM 2026-09-21 (oracle era - corrections, see W2_decode_atom_2026-09-21.md)

The oracle revealed this cell's v1 bench deviated from shipped math in two
perf-relevant ways: u1 index l0+4 (vs l0+1) and, decisively, a missing
kby=kbx*8 y offset that made all 8 x-int loads LOOP-INVARIANT (compiler
hoisted them out of the kbx loop). The 105.2 GB/s "shipped clone" figure was
therefore an accidentally lighter kernel; same-era A/B against the fixed
clone: 360.0 us/106.6 vs 424.6 us/90.4. Number of record for the shipped atom
on this cell is 90.4-90.9 GB/s (today-era; yesterday's package-load state
differed). The seven schedule negatives and the consume-ablation LADDER SHAPE
stand; the full-depth decode-atom ladder (8 arms, all oracle-passing, all
negative except the clone itself) is in W2_decode_atom_2026-09-21.md.
