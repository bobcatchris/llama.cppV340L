# T4 Producer Receipt: q8_1 Activation Cache (zero-GPU phase) - 2026-09-21

Desk: wt-t4-producer, branch amd/t4-producer. Target W0-T4: kill the
redundant activation re-quantization in decode. Census basis:
results/W0_census_decode_receipt.md - quantize_q8_1 = 7.1% of decode
kernel time, ~1400 launches/step (all 3 dies); within one layer 8+ vec-q
matmuls consume 2-3 unique x (GDN: wqkv + wqkv_gate + ssm_beta +
ssm_alpha share the norm output; attn: q/k/v share one input; FFN
gate+up share the post-attn-norm output).

## What was implemented

Env-gated per-ubatch q8_1 activation cache in the CUDA backend
(`GGML_CUDA_Q81_ACT_CACHE=1`, static-once getenv, off by default - zero
behavior change when unset):

1. ggml/src/ggml-cuda/common.cuh - `struct ggml_cuda_q81_act_cache`
   (host-only), member `q81_act_cache` of `ggml_backend_cuda_context`.
   Key = (producing ggml_tensor node, src1 data ptr, ne10-13, src1 row
   strides, device, stream). 64 MiB byte cap (stop-inserting, no
   eviction), hit/miss counters, INFO log line every 256 computes.
2. ggml/src/ggml-cuda/ggml-cuda.cu:
   - `ggml_cuda_q81_act_cache_enabled()` static-once env check.
   - `ggml_backend_cuda_graph_compute`: `begin_compute(enabled &&
     !use_cuda_graph)` per graph compute - clears all entries and (re)arms.
   - `ggml_cuda_op_mul_mat` split path (the TP3 route): on hit, reuse the
     cached q8_1 for src1 (no alloc, no quantize launch); on miss,
     quantize into a cache-owned pool buffer; on disabled/full, upstream
     per-call alloc + quantize exactly as before.
3. ggml/src/ggml-cuda/mmvq.cu - `ggml_cuda_mul_mat_vec_q` non-split path:
   same hit/miss/fallback structure (ids==nullptr only).

## Safety design (the part that matters)

- Buffer-reuse defense: ggml-alloc free-block reuse (ggml/src/ggml-alloc.c)
  can hand a freed intermediate's address to a later same-shape tensor
  WITHIN one compute. A data-pointer-only cache would false-hit. The key
  therefore carries the producing tensor NODE; two different nodes at the
  same address can never collide. The mul_mat_id scratch slices (stack
  tensors, op==GGML_OP_NONE) are excluded by `cacheable()` and by the
  ids!=nullptr check.
- Lifetime: entries live only until the next `ggml_backend_cuda_graph_compute`
  entry, where `begin_compute` frees every buffer back to its ggml_cuda_pool
  and clears the map - before any op of the new compute allocates. No entry
  can outlive the compute buffer its x lives in; nothing is freed from
  destructors (the pool destructor owns all device memory at teardown).
- CUDA graphs (this build defines GGML_HIP_GRAPHS): the cache is
  force-inactive during capture AND replay. During capture every quantize
  must run in-graph (a hit would bake a pointer into the graph while the
  quantize kernel stays out of it - replay would then consume stale q8_1);
  during replay the host side does not run at all. With graphs disabled or
  not-yet-warm (the V340L situation, census: "graph-capture door stays
  closed"), the cache is active for direct execution only.
- Bit-exactness: quantize_q8_1 is deterministic (no atomics, every padded
  byte written, scale/sum from a fixed butterfly order). Same key fields +
  unchanged x => byte-identical output. Consumers read the q8_1 with
  layout derived only from keyed values (ne10_padded/QK8_1 strides), so
  hits feed the mmvq kernels exactly the bytes a fresh quantize would.
- Ordering: keys include the producing stream; the split path quantizes on
  ctx.stream(id,0) and the existing event/wait machinery orders consumers
  exactly as it does for a fresh quantize.
- MMQ untouched: hooks gate on `quantize_src1 == quantize_row_q8_1_cuda`.

## Expected saving (math of record, device confirmation deferred)

- Before: ~1400 quantize_q8_1 launches/step (~466/die), one per matmul
  call per die; each x re-quantized 3-4x per layer.
- After: one quantize per unique x per layer per die - ~2-3 unique x per
  layer vs 8+ matmul quantizations today => ~450-500 launches/step
  (~150-170/die), i.e. ~63-65% of quantize launches removed.
- Kernel-budget bound: 7.1% x (1 - ~0.36) ~= 4.5% of decode kernel time.
  On the 12.24 t/s baseline (~87 ms/step) the optimistic bound is
  ~+4-5% decode t/s (~12.8 t/s) if fully realized; host-side cost is one
  hash lookup per matmul call (negligible vs 93 us kernels).
- Second-order: q8_1 write traffic drops ~3x (5120-float x -> 5760-byte
  q8_1 per launch) and 900+ fewer kernel launches/step across dies.

## Open risks

1. In-compute mutation assumption: a cached node's x must not be written
   between two of its matmul consumers. Same assumption class upstream
   CUDA-graph replay already makes (pointer stability, content-only
   change). No transformer/GDN decode graph mutates norm outputs in place;
   the served determinism gate below is the empirical check.
2. TP3 peer copies: dies that receive q8_1 via peer-copy now copy from the
   cached buffer on the producing die; copy count unchanged, ordering via
   the unchanged event machinery.
3. VRAM: pool-held cache bytes, <= 64 MiB cap, expected ~1-2 MB in decode.
