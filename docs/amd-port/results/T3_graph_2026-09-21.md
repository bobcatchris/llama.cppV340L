# T3 Reopen Receipt: grouped mmvq formation under the TP3 meta machinery - 2026-09-21

Desk: wt-t3-graph, branch amd/t3-graph. Zero GPU (mechanism + fix + host tests;
device validation deferred). Closes the E-042/E-044 "grouping never forms"
finding with a host-proven mechanism, an implemented fix, and the instrument
that makes formation observable in the next window.

## Mechanism of record

**The graph allocator recycles the first tiny member's dst range for the
second, and the grouped path's aliasing safety checks drop the pair.** On the
real ggml_gallocr allocation of the qwen35 GDN-layer shape (T=1x1 decode,
Qwen3.8-27B census dims), the ssm_beta and ssm_alpha MUL_MAT dsts land at the
IDENTICAL address (192 B block; host proof below), so
`ggml_cuda_mmvq_group_overlap(cand, head)` fires, the candidate is dropped,
n stays 1, and `ggml_cuda_try_group_mmvq` returns false for every GDN layer on
every die. The rejection is CORRECT for the early-write design (the grouped
launch would write alpha's result into the range the sigmoid still needs to
read as beta) - the design needed copy-back, not a weaker check.

Host proof (zero GPU, real gallocr, CPU buft; docs/amd-port/tests/
test_t3_detect_host.cpp, ALL PASS): the exact build_layer_attn_linear chain
(qkv MM -> z MM -> beta MM -> reshape4d -> sigmoid -> alpha MM -> reshape3d ->
add(ssm_dt) -> softplus -> mul(ssm_a) -> consumers) allocates
`beta dst == alpha dst` (e.g. 0x7cf177eb3040 both). The naive short chain
(test_t3_alias_host.c) does NOT recycle - the sigmoid's inplace-reuse keeps
beta's block - which is why a careless probe refutes the mechanism; the order
and the downstream inplace users decide it. The full chain recycles.

## Hypotheses of record examined (E-042 named "concurrent events and/or eligibility")

1. REFUTED - concurrency gate: `concurrent_events` is only ever populated in
   `ggml_backend_cuda_graph_optimize`, which resets the map and returns early
   unless GGML_CUDA_GRAPH_OPT=1 AND `ggml_backend_cuda_get_device_count() == 1`.
   Served: 3 devices (HIP_VISIBLE_DEVICES=0,1,2), env unset -> the gate is
   inert under TP3. The meta-backend butterfly never creates events.
2. REFUTED - meta subgraph partitioning hides the pairs: per-device subgraphs
   are index-range copies of the unified node order
   (`cgraph_main->nodes[k] = bcj.nodes[i_node_start+k]`), and the per-device
   simple tensors are stable per (tensor, device)
   (`stc.simple_tensors[tensor][j]`), so same-src1 POINTER identity holds in
   every per-device subgraph. The 16-node window sees beta/alpha co-located
   (3 nodes apart in the built graph).
3. REFUTED - shape gate: the served decode is T=1x1x1. Census evidence: every
   quantize_q8_1 grid is (X, ne1=1 or 8, Z=ne2*ne3=1) and every tiny
   mul_mat_vec_q is the ncols_dst=1 template -> src1 ne[1]=ne[2]=ne[3]=1.
   The eligibility whitelist passes.
4. PROVEN structural blocker #2 - row whitelist vs attn k/v: the TP3 meta
   splitter gives kv weights granularity
   `lcm(n_embd_q=1536, blck_perf=256)/n_gqa=6 = 512`, so attn_k/attn_v
   [5120x1024] shards are 512 rows/die (or 0 on the rotating third die, where
   the node's compute flag is cleared). Default GGML_CUDA_MMVQ_GROUP_MAX_ROWS=
   256 aborts every {attn_k, attn_v} group; E-025's planned "MAX_ROWS=384
   sweep" would ALSO have failed - the correct sweep value is 512.
   attn_q (3072-6144/die), attn_qkv (~3328-3584/die), attn_gate (2048/die)
   stay above any sensible whitelist.
5. Census instrument gap: the ON-arm census (census_decode_20260921_224043)
   has no artifact proving GGML_CUDA_MMVQ_GROUP reached the bench (the enable
   INFO line is filtered at default verbosity; census_decode.sh has no env
   plumbing), while the served ON arms verified delivery via /proc but carried
   no launch-count instrument. With the mechanism above, both arms are
   consistent; the new DEBUG instrument removes this ambiguity permanently.

## Fix implemented (same env switch, GGML_CUDA_MMVQ_GROUP=1)

ggml/src/ggml-cuda/ggml-cuda.cu only:

1. Copy-back members: a same-src1 candidate whose dst aliases an earlier
   member (or fails an intermediate WAW/WAR check) is no longer dropped - it
   is admitted as a copy-back member: `ggml_cuda_group_mmvq_exec` writes it
   into a per-device pool temp inside the grouped launch, and the graph loop
   issues one D2D `cudaMemcpyAsync` temp->dst at the member's OWN graph
   position (solo timing; capture/replay-safe; the temp lives in the compute
   pool, disjoint from graph ranges). The head and genuinely disjoint members
   keep the unchanged direct early-write. New hard rules for copy-back
   members: rejected over split buffers (legacy multi-device path keeps the
   strict rules) and when the dst lives off the computing device.
2. Safety split: new `ggml_cuda_mmvq_group_x_fusion_safe` (shared-x mutation +
   fusion-span exclusion - hard for BOTH classes) factored out of
   `ggml_cuda_mmvq_group_safe_candidate` (full direct-write safety).
3. GGML_CUDA_MMVQ_GROUP_DEBUG=1: gate-naming tracing at WARN level (survives
   the server's default verbosity filter, unlike the enable INFO line) with a
   64-line process budget: decline reasons name the exact gate (concurrency,
   x-mutation, fusion span, split-ness, copy-back-over-split, off-device dst,
   whitelist with the row count and the 512-granularity hint, geometry), and
   formations print members/rows/types/direct-vs-copy-back. This is the
   instrument that closes the E-042 evidence gap in one boot.
4. Bit-exactness unchanged by construction: every member still runs the
   verbatim solo mul_mat_vec_q schedule; a copy-back member's real dst content
   equals solo (temp written by the same schedule, bitwise copy, same write
   position in the graph). Launch accounting for the served beta/alpha pair:
   2 quantize + 2 mmvq -> 1 quantize + 1 grouped mmvq + 1 D2D copy.
5. Env unset: zero behavior change (the scan exits at `!cfg.enabled` before
   any new code runs).
