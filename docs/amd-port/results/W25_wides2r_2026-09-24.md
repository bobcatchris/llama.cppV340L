## 1. DESIGN

Today (pre-C3), in the share branch of mul_mat_vec_q the token loop issues
ONE s2r preload per token and immediately consumes it:

- iq3_s:  preload mmvq.cu:613 (pre-C3 :596), apply_u right after
- iq3_xxs: pre-C3 :626; iq4_xs: pre-C3 :656; q4_K: pre-C3 :704; q5_K: pre-C3 :735

`const mmvq_yw8 w = vec_dot_*_q8_1_preload(&y[j*stride_col_y + kby], kqs);`
inside `for (int j = 0; j < ncols_dst; ++j)`. The compiler schedules each
token's y loads against its use to cap VGPRs, so the y-side memory pipeline
serializes per token: one 36 B preload in flight per lane-iteration at T=4.

C3 wide-s2r: a new trailing template bool `WS2R` on mul_mat_vec_q selects a
variant that first issues ALL ncols_dst preloads into a per-token register
array (`mmvq_yw8 w[ncols_dst]` / `mmvq_ywq2 w[ncols_dst]`), then runs the
identical apply loops. Per lane-iteration at T=4 that is 4 x 36 B of y
traffic in flight inside the same kbx schedule - the W23 C3 mechanism
(attack M1 y-side MLP + M3 y-broadcast redundancy together).

Bit-exact by construction: the preload calls read the same addresses
(&y[j*stride_col_y + kby], same kqs), the apply calls run in the same (j, i)
order with the same dec/scale/d operands, the kbx loop and the tmp[j][i]
accumulation sequence are untouched. Only load timing moves; no arithmetic
reassociation anywhere.
