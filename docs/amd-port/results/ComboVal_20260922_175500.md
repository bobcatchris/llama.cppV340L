## 3. Admission validation (E-054 server fix, probe_kv_admission.py)

One boot at -c 10240 (same line otherwise, kv unified default verified:
"n_parallel = 4 and kv_unified = true", "kv_unified = true"). Probe:
two ~7.9k prompts fired concurrently, n_predict 16.

  request A: http 200 in 80.1s
  request B: http 0 in 600.1s (probe client timeout)
  log: defer-lines=2 exceeded-lines=0 http500~=0
  probe verdict line: FIX FAIL: non-200 response

MECHANISM ENGAGED, both defer decisions verbatim:

  2.38.539.670 W unified KV occupancy is too high, defer task 2 (n_need = 7862, n_used = 512, n_pending = 7345, n_ctx = 10240)
  3.54.814.661 W unified KV occupancy is too high, defer task 2 (n_need = 7862, n_used = 7872, n_pending = 0, n_ctx = 10240)

zero "Context size has been exceeded", zero HTTP 500, A completed clean
(prefill 78.7 s / 99.8 t/s, mean acc len 3.00).

DEFECT FOUND - the deferred request STARVES: at the second defer, A had
released with its 7872-token KV RETAINED by the prompt cache (slot selection
line: "selected slot by LCP similarity, sim_best = 0.999 (> 0.100 thold),
f_keep = 0.998" - B is A's prompt plus a 5-token suffix). The admission
formula counts B's FULL n_need = 7862 against n_used = 7872 and defers
forever, although B's incremental need is ~5 tokens against 2368 free - the
raw count gives no credit for the 7857 prefix tokens already cached. No
eviction path exists, so B is never scheduled; at 12.34 min the server
logged "cancel task, id_task = 2" when the probe's 600 s client timeout
closed the connection. The probe's "runs after the other finishes"
expectation fails not because the defer is wrong but because there is
nothing for the defer to yield to. Fix direction for the admission desk:
credit prompt-cache prefix reuse in n_need (admit when incremental need
fits), or add a cache-eviction fallback after N defers. The --control mode
(left for a later window per the brief) would also be affected by this
starvation and should run only after the fix.
