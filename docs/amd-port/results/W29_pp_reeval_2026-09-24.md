## 3. A3 - STRUCTURAL MATH: PP4 decode round under the current stack

Setup: -sm layer, 4 stages x ~16 target layers + nextn block on the last
stage. Flag verified: common/arg.cpp:2541 {"-sm", "--split-mode"},
"{none,layer,row,tensor}" -> LLAMA_SPLIT_MODE_LAYER; classic sched path
(src/llama-context.cpp:415-425 auto-enables sched pipeline_parallel for
sm layer + offload, which can overlap PREFILL ubatches - decode has one
ubatch per pass, nothing to overlap).

### 3.1 The one mechanism that decides it: compute serialization

Full-model compute work per MTP cycle F = 4 dies x C ~ 4 x 82 = ~330
ms-die (each die computes its 1/4 shard of every layer; dies run
concurrently in TP4, wall pays C).

- TP4 cycle wall ~ C + NCCL 31 + host/draft/gaps ~20 = ~124 ms. 
- PP4 cycle wall = 4 stages SERIAL: 4 x C = ~330 ms of compute + ~1 ms
  handoffs + host/catchup/draft/gaps ~20 = ~350 ms.

The boundary wall (-31 ms) is bought with 3 x C (+245 ms) of serial
compute. Net +215 ms/cycle NO MATTER how cheap the handoffs are.

Sensitivity: even at an optimistic C = 60 (a -30 percent compute
improvement that does not exist in the banked data), PP4 = 4 x 60 + 25 =
~265 ms/cycle = 87 ms/token = 11.5 t/s, still -53 percent vs 24.55.
The kill is structural, not parameter-tuned.

### 3.2 Predicted PP4 round (short decode, current kernels)

cycle = 4C (~328) + stage handoffs + draft/catchup deltas + host ~10.5:

| term | ms | note |
|------|----|------|
| verify compute 4 x C | ~328 | section 3.1 |
| stage handoffs (3/pass x 2 passes) | ~1 | 12 x 80 KB fp32 (ne 20480 = 5120 x 4 tok) P2P copies, latency-class ~40-80 us each incl. sched event/sync slop |
| catch-up unsharded on stage 3 | +5 | 2.3 -> ~9 (MMVQ 1.2->4.8, flash 0.74->3.0) |
| draft loop unsharded on stage 3 | +9 | per step block MMVQ 0.43->1.7 + head 0.695->2.8 (lm_head q6_K 0.58 GB no longer 4-way sharded); 3 steps |
| host slice + gaps | ~10.5 | unchanged |

### 3.3 Draft-mtp chain x PP staging (the never-analyzed interaction)

Trace: under -sm layer the nextn block and output head are appended at
the END of the model - they land on the LAST stage (die 3), so the 3
draft steps do NOT walk the pipeline (0 stage traversals, not 6 x 4).
The chain cost is instead UNSHARDED compute: today the draft side is
sharded 4-way (6 draft boundaries at 20 KB, 89.9 us; head sharded by
vocab). Under PP every draft step runs the whole nextn block + full
lm_head on one die: +3.4 ms device/step x 3 = +10 ms/cycle, and the
draft-side boundary count drops 8 -> 0. Worst case (a PP variant that
did spread nextn across stages) = 24 traversals x ~0.05-0.1 ms = 1.2-2.4
ms - also bounded small. Either way the draft-chain term is noise
against the 3 x C serialization. The interaction is real but NOT the
decision-maker.

Also note: acceptance (0.68) is untouched by PP - same numerics class
per stage (no cross-die reduce of a given tensor at all), but boot-to-
boot determinism sha WILL change (different reduce topology, per-die
full-tensor sums) = a new signed-off-numerics-class question for free.

### 3.4 External validation: the early prefill number agrees

Prefill is compute-bound; PP serializes it the same way (width 1). Early
measurement: TP3 tensor prefill 135.77 vs layer-split 60.39 = PP at 0.44x
= exactly the 1/N-stage class with partial ubatch overlap from the sched
pipeline mode (llama-context.cpp:417). Decode has no such overlap to
lose less. The one PP datapoint that exists supports the mechanism.

### 3.5 PP4 at depth

C(D) grows with depth (attention law). At 100k: law round ~303 ms =>
C ~ 250; PP4 cycle = 4 x 250 + ~25 = ~1025 ms = ~337 ms/token = ~3.0 t/s
vs TP4 ~10.0 t/s. At 199k: round ~498 => C ~ 435; PP4 cycle ~1765 ms =
~580 ms/token = ~1.7 t/s vs TP4 ~6.0 t/s. The PP loss ratio WORSENS with
depth (72 percent loss vs 65 at short) because deep attention compute is
also serialized. No depth rescues PP.

## 6. A4 - VERDICT: NO-GO (both windows)

The kill math, for the record, so the question stays closed:

1. TP4 short decode of-record: 24.55 t/s = ~124 ms/cycle, of which the
   boundary wall is 29-31 ms (24-25 percent) and per-die compute C is
   ~80-85 ms paid CONCURRENTLY (width 4).
2. PP4 replaces the wall with serial compute: cycle = 4C + ~31 saved
   NCCL - handoffs ~ 350-365 ms => 8-9 t/s (-63 to -68 percent). To beat
   24.55 t/s, PP4 would need 4C + 25 < 124, i.e. C < 25 ms - a per-die
   non-NCCL cycle compute 3.3x better than measured. The banked physics
   forbids it: the MMVQ stream alone is 3.06 GB/die at a 70-120 GB/s
   access-pattern ceiling (W5) = 25-44 ms minimum for MMVQ alone, before
   flash, small kernels, host, or draft.
3. tp2xpp2: same trade at half depth - buys ~14 ms of boundary wall,
   pays +82 ms of serialization, is not implementable without a new
   sharding subsystem, and cannot boot at 200k regardless (section 4.4).
4. The early-era "PP lost" verdict is thereby REPLACED by a real one:
   the early artifacts never measured PP decode (crash), but the banked
   census decomposition proves PP decode loses ~3x under ANY kernel
   stack of this campaign. Kernel progress (fa40, s2r, share) shrinks C,
   which makes PP WORSE, not better - the serialization tax scales with
   the thing being optimized.
