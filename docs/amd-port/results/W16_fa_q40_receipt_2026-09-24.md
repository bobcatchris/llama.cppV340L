Served geometry (W11 P0, re-pinned by bench_attn_real.cu): DKQ=DV=256,
flash_attn_tile<256,256,4,2,false> (NOTE: the desk order said "<256,256,16,2>";

KV flow (q4_0 cache -> attention, every decode step, every layer):
1. The KV cache stores q4_0 (-ctk/-ctv q4_0). The graph hands the q4_0 K/V
   views DIRECTLY to the flash_attn_ext node - there is NO graph-level cast.
2. Dispatch: ggml_cuda_flash_attn_ext (fattn.cu:582) ->
   ggml_cuda_get_best_fattn_kernel (fattn.cu:374). On gfx900 (no
   turing/volta/wmma/mfma), K->ne[0]=256, K->type==V->type==Q4_0: the
   quantized vector-kernel branch requires Q->ne[1] <= 2 (fattn.cu:515-519),
   so T=4 falls through to BEST_FATTN_KERNEL_TILE (fattn.cu:521). The vec
   kernel WOULD read q4_0 natively (FATTN_VEC_CASES_ALL_D(Q4_0,Q4_0),
   fattn.cu:239-241; need_f16 only for F32, fattn.cu:559-562) - i.e. a T<=2
   workload on this stack already has a q4_0-direct path; T=4 does not.
3. TILE forces need_f16_K=need_f16_V=true (fattn.cu:538-543), and
   ggml_cuda_flash_attn_ext_get_alloc_size (fattn.cu:532-571) + 
   ggml_cuda_flash_attn_ext_get_f16_extra_data (fattn-common.cuh:53-85)
   reserve the "f16-KV-pool" as bytes appended to the KQV tensor allocation
   (dst end, 128-padded, K pool then V pool). THERE IS NO PERSISTENT POOL -
   it is dst-append scratch, one full-depth f16 copy of K and V per node.
4. Per launch: launch_fattn (fattn-common.cuh:969) converts the FULL K and V
   tensors via to_fp16_cuda = ggml_get_to_fp16_cuda(Q4_0) =
   dequantize_row_q4_0_cuda (convert.cu:529-533) -> dequantize_block_q4_0
   kernel (convert.cu:85-106), grid ceil(k/256) x 32 threads, one launch per
   tensor per layer per step over the FULL ne11. This is the W15-measured
   linear pool dequant (3.98 us/1k tokens/launch; 2 launches/layer/step).
   nb11/nb12/nb13 are then rescaled to f16 strides (fattn-common.cuh:1029-1043).
5. flash_attn_tile reads the f16 pool: K_h2/V_h2 half2 pointers
   (fattn-tile.cuh:864-865), tile loads = 16 B half2 copies into shared
   KV_tmp (flash_attn_tile_load_tile, fattn-tile.cuh:380-427), KQ = half2
   mad chain (fattn-tile.cuh:485-557), V tiles likewise (fattn-tile.cuh:
   723-724). Parallel-block scan + flash_attn_combine_results<256>
   (fattn-common.cuh:911-967, launched fattn-common.cuh:1260-1268).

WHAT A Q4_0-DIRECT TILE MUST DO (design):
- Host: same launch_fattn<256,4,2> chain with need_f16_K/need_f16_V = false ->
  K_data stays q4_0, nb11..nb13 stay q4_0 byte strides (256-dim row = 8 blocks
  x 18 B = 144 B, 16 B-aligned rows). No pool reads, no dequant launches.
- Kernel: template tag q40_kv on flash_attn_tile (+ load_tile + iter_KQ +
  iter). The q4_0 loader reads one block (18 B: 1 half d + 16 B qs) per
  thread per iteration and writes the SAME half2 shared tile layout the f16
  loader produces. Dequant formula = dequantize_V_q4_0 (fattn-common.cuh:
  409-445): nibbles -> __vsubss4(-8) -> half2 multiply by __half2half2(d).
- NUMERICS PREDICTION: BIT-EXACT vs the pool path. The pool kernel computes
  d*(q-8) in f32 and rounds once on half store (convert.cu:99-104); the
  in-kernel half multiply rounds the identical exact product once. Same
  halves into an untouched KQ/VKQ pipeline. To be proven by device oracle.
- Instance law: same <4,2> geometry, same LDS, same occupancy -> same grid
  (1,37,3); it is a NEW kernel object though, so the W14 E1/E2 start-latency
  class must be checked (base-vs-direct interleaved timing = contagion-
  sensitive pattern by construction).

TRAFFIC MODEL (per KV element per decode round, attention+dequant class):
pool path: deq read 0.5625 + deq write 2.0 + tile re-read 2.0 x 3 z = 8.56 B;
direct: 0.5625 x 3 z = 1.69 B -> 5.1x fewer DRAM bytes. At W11's 30.5 GB/s
effective the model predicts a large win; the kernel must prove it end-to-end.

2. A2 - VERDICT: FAIL (numerics gate; fail-closed)

The direct arm's attention output is WRONG on gfx900/ROCm 6.2, and the
wrongness is the desk's primary finding:

- Oracle: 6144/6144 dst elements differ from the served path in every
  session; the error class shifts with innocuous code/build changes
  (max rel 3.7e+02, 6.3e-01, 1.6e+06, all-NaN across builds) while
  base-vs-basedup stays bit-exact - i.e. deterministic per binary,
  not a data race.
- Staged in-kernel forensics (temp GGML_FATTN_Q40_DBG hooks, sink
  channel = unused kernel arg): shared K tiles (both chunks), shared V
  tiles, consumer K_k registers (both chunks) and Q_k registers (all
  16 k_KQ_1 positions) are ALL bit-exact vs the pool-path values -
  yet KQ_acc diverges 64/64 rows from base at the first chunk.
- 100 consecutive direct launches with per-launch sync checks: no
  faults. pb=1 (combine skipped): still wrong -> not the combine.
  -O2: identical divergence -> not an -O3-specific optimizer fault.
  Removing __restrict__ from the loader, and a full rewrite of the
  loader in the f16 loader's exact loop shape: dust unchanged ->
  not the loader structure.

Conclusion: a codegen-class defect specific to this template
instantiation on gfx900/ROCm 6.2 (hipcc/clang 18) - same device-vs-
toolchain reality-gap family as E-110's v_perm_b32 finding, but a
correctness (not feature) gap. Root cause NOT localized to an ISA
sequence within this desk's budget; left as an open item with the full
instrumented harness documented here. The A2 bar (>=25% end-to-end
win with byte-exact or owner-flagged numerics) is NOT MET: numerics
fail first, and the perf number cannot be trusted while the kernel
computes wrong values.
