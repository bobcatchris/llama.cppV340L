# T3 Receipt: Grouped Multi-Tensor Decode GEMV (zero-GPU phase) - 2026-09-21

Desk: wt-t3-grouped, branch amd/t3-grouped. Target W0-T3: the tiny-tensor tax
(~12-15% of decode step in launch + DRAM latency floors; ~250 q4_K + ~114 q8_0
+ iq3 tiny calls/step at 5-42 us/call on <1 MB total; results/
W0_census_decode_receipt.md). Within one GDN layer several tiny matmuls consume
the SAME x (norm output feeds wqkv, wqkv_gate, ssm_beta, ssm_alpha).

## What was implemented

Env-gated grouped decode GEMV (`GGML_CUDA_MMVQ_GROUP=1`, static-once getenv,
off by default - env unset = zero behavior change): one kernel launch computes
a batch (2..8 members) of small quantized vec-q MUL_MAT nodes that share the
same src1. Each member keeps the EXACT solo mul_mat_vec_q schedule, so per-
tensor results are bit-identical to the ungrouped path by construction.

1. ggml/src/ggml-cuda/mmvq.cu:
   - `mul_mat_vec_q_grouped` kernel, grid (max member rows, n_members),
     block (warp_size, nwarps). Per block: member m = blockIdx.y, row =
     blockIdx.x, early-out past the member's rows; switch over the member's
     ggml_type dispatches to `mmvq_group_row<type>` - a verbatim copy of the
     solo kernel's body for ncols_dst=1, has_fusion=false, small_k=false
     (same kbx partition tid/(qi/vdr), same blocks_per_iter = vdr*nwarps*
     warp_size/qi, same kqs, same shared-mem order, same warp_reduce_sum<64>
     butterfly). nwarps is read from blockDim.y; mixed types in one launch.
   - `ggml_cuda_mmvq_group_geometry_ok` (host): groups are only taken when all
     members active on a device share the solo launch geometry - uniform
     calc_nwarps(type, 1, table_id), calc_rows_per_block == 1, and NOT the
     small_k schedule (formula + NVIDIA iq exceptions mirrored from
     mul_mat_vec_q_switch_ncols_dst). gfx900 (GCN table): nwarps = 2 for every
     type at ncols_dst=1, so all-census types pass.
   - `ggml_cuda_mul_mat_vec_q_grouped` launcher. Member parameters travel as a
     by-value kernel arg struct (8 x {vx, dst, type, ncols_x, nrows_x,
     stride_row_x} ~ 292 B): capture/replay-safe, no host memory held across
     graph replay (the T4 stale-pointer lesson applied to launches).

2. ggml/src/ggml-cuda/ggml-cuda.cu (grouping point = graph-level node loop,
   precedent: ggml_cuda_try_fuse's multi-node consumption):
   - `ggml_cuda_try_group_mmvq` at node i: head must be vec-q eligible
     (MUL_MAT, no ids, f32 x/dst, quantized contiguous src0, T=1 shapes
     ne11=ne12=ne13=1, no FWHT hint, no recycled-padding src0). Scans up to 16
     nodes ahead for members: same src1 POINTER (byte-identity, the T4
     node-key law), eligible, not the start of any try_fuse MUL_MAT pattern
     (5/3/2-node spans, vec_fuses gate - so fusion stays exclusive and split-
     buffer nodes that can never vec-fuse stay groupable), not inside a fusion
     span starting at an intermediate, split-ness uniform.
   - Liveness safety for the early dst write (executing members j > i at
     position i): every intermediate node k in (i, j) must (a) not write any
     range overlapping dst_j (WAW), (b) not read any range overlapping dst_j
     (WAR), (c) not write src1's range (x mutation between members); plus all
     member dst ranges pairwise disjoint (ggml-alloc can recycle a dead
     member's range for a later member). Range test = alloc-size overlap,
     same style as ggml_cuda_check_fusion_memory_ranges. Any failure drops
     just that candidate; the window keeps scanning.
   - `ggml_cuda_group_mmvq_exec`: faithful mirror of ggml_cuda_op_mul_mat
     restricted to the vec-q T=1 path (single src1 col block), per device:
     verbatim row_low/high split math, one shared q8_1 quantization of x per
     device (T4-cache find/insert with the SAME key when GGML_CUDA_Q81_ACT_
     CACHE is on - the two features compose; plain pool buffer otherwise),
     one q8_1 peer copy per device for the whole group (not per member), one
     grouped kernel launch per device over that device's active members, then
     per-member dst peer copies and the verbatim event record/wait fencing
     (main-prep events, peer done events, final main waits). Whitelist gate:
     any member's per-device row range > GGML_CUDA_MMVQ_GROUP_MAX_ROWS
     (default 256, env-tunable) aborts the whole group to solo, no partial
     groups. Fail-loud GGML_ASSERTs re-verify every gate inside the runner.
   - Node-loop hook: fresh per-pass `mmvq_group_done` set; grouped members
     are marked done and skipped; the head node is consumed by the group.
     Disabled entirely when concurrent_events are active (never reorders
     around the multi-stream machinery).

Group size is 2 in the census world (ssm_beta + ssm_alpha per GDN layer, both
5120x48, whole tensor on one die after the row-rounding collapse); up to 8
members are supported. wqkv/wqkv_gate share the same x but sit above the row
whitelist and stay solo by design (they are efficient big cells).

## Bit-exactness (by construction, host-oracled)

Each grouped row runs the identical instruction sequence as the solo kernel
for its member: same kbx -> thread partition, same kqs, same accumulation
order, same two-warp shared reduction and butterfly, same vec_dot from
vecdotq.cuh. The shared q8_1 of x is one quantize_row_q8_1 launch - the T4
byte-identity argument verbatim (quantize is deterministic, type_src0 unused
by the vec-q quantizer, so one buffer serves all member types).

## Expected saving (math of record; device confirmation deferred)

- Census basis: ~250 q4_K + ~114 q8_0 + iq3 tiny calls/step (3 dies) at
  5-42 us/call, ~12-15% of step in launch + latency floors. Tiny tensors
  (ne01=48 < row rounding) collapse onto one die per member op, so per-step
  per-die the GDN beta/alpha pairs are 96 solo launches -> 48 grouped launches
  (2x cut on the pair class; g members -> 1 launch per device generally,
  g up to 8).
- Latency: within one launch the members' weight loads co-reside, so the pair
  time approaches max(member times) instead of the sum: both members sit at
  the 5-42 us latency floor today. If the same-x pair class holds ~half of
  the tiny-tensor mass (~6-8% of step), halving it saves ~3-4% of decode
  kernel time; the whole-class optimistic bound stays the census 12-15%.
- Second-order: one quantize per group instead of per member (independent of
  T4; composes with it), one q8_1 peer copy per device per group instead of
  per member, and per-member event round-trips collapse.
- On the 12.24 t/s baseline the optimistic bound is ~+2-5% decode t/s if
  fully realized. Promotion bar stays >= +2% measured.

## Open risks

1. Cache-key class (T4 lesson): grouping keys on src1 node/pointer identity,
   never on recycled addresses; the recycled-address hazard reappears as
   dst-range recycling between members, which the pairwise overlap check
   rejects. In-compute x mutation between members rejects the candidate.
2. Fusion interaction: any try_fuse pattern that would consume a member or
   span it excludes the candidate; on split buffers vec_fusion can never
   trigger (should_fuse_* return false), so GDN pairs stay groupable.
3. Occupancy: the grouped kernel carries __launch_bounds__(512,1) vs the
   solo kernel's exact 128-thread bounds on gfx900; register allocation may
   differ (perf question, not correctness). Measured in the die-3 window.
4. CUDA graphs: grouped launches are capture-safe (by-value params, pool
   buffers per compute); replay skips the host loop entirely. If the
   graph-capture door opens (today it stays closed per census), the capture
   pass executes groups exactly like direct execution.
5. The head node is executed early; the window scan + liveness checks bound
   the reordering to 16 nodes of graph distance.
