## (b) TOP hypothesis for the ~16 ms — with the strongest code evidence

**The 16.3 ms/round classed "accept/align/propose bookkeeping" is NOT the book window
(code-priced µs above). It is the ONE-SHOT COLLECTIVE PER-CALL HOST-DRAIN PATTERN: every
one-shot AR/argmax call on the round path ends in a hard `cudaStreamSynchronize` +
mapped-status poll, serializing host enqueue against device execution 8× per round.**

Strongest evidence:

1. **one_shot_argmax.cu:567-570** — every `allreduce_argmax` runs
   `for (int try_no = 0;;) { CUDA_CHECK(cudaStreamSynchronize(stream)); const int pending
   = *impl_->host_status[rank]; if (pending == 0) {…break;} … }` — a minimum of ONE hard
   stream drain per call, with the code's own comment "cost ~ the call itself" at its twin.
2. **one_shot_allreduce.cu:808-811** — the AR twin, same in-loop
   `cudaStreamSynchronize` per call ("Consume the call's own status: force the stream to
   run the kernel … cudaDeviceSynchronize is the narrowest sync that guarantees the
   LEADERs ran; cost ~ the call itself").
3. **Call census at k=2/T=3** — 7 one-shot collectives per steady round, each carrying one
   drain, plus the accept drain = **8 hard drains/round**:
   verify ar_argmax :3164 (1) · align fwd ARs text_context_impl.h:1232,1241 (2) ·
   propose d0 :3567 (1) · chain fwd ARs (2) + chain head :3650 (1) · accept :3222 (1).
4. **B1 anchor fit** — align 8.03 ms = 2 drains + ~1 ms true T=1 device work (MTP-layer
   weight read ≈ 0.5-0.7 GB/s-class pass + kvarn attend); chain AR 7.85 = 3 drains;
   propose 0.31 = 1 drain on a near-empty stream (cheapest). Drains price at ~2-2.6 ms
   each once peer-lag retries are included (G18c retry histogram 224/77/55/38/24/13/3/1,
   one_shot_allreduce.cu:763-770 — retries are COMMON, and each retry = kernel relaunch +
   another full sync).
5. **Why a drain costs ms, not µs**: the T=1 draft-side spans are HOST-ENQUEUE-BOUND
   (~25-35 launches per forward through the HIP path at ~5-15 µs each ≈ 0.3-0.8 ms host
   per segment, plus shape checks/Scoped bindings/workspace). A per-call drain cuts the
   pipeline at every collective: the device finishes call N's kernel + handshake, goes
   IDLE, and stays idle while the host re-walks the next segment's enqueue. 8 drains
   quantize the round into 9 host-paced segments — the device-visible cost is exactly the
   exposed enqueue+handshake latency the align/chain B1 anchors show.
6. **The M2 premise itself is evidence**: M2_NOTES calls :3222 "the round's ONLY hard
   stream sync" — that is true only of the SYNC SITES IN tp2_backend.cpp; the one-shot
   calls hide 7 more drains inside op boundaries, where the op event pairs (align,
   chain_fwd, chain_head, propose, ar_argmax) will price them.

Prediction for the in-flight M2 read: **book ≪ 1 ms on every rank**; the draft-side class
shows up as align ≈ 8 + chain_fwd+chain_head ≈ 7.9 + propose ≈ 0.3, with `sync` small and
the inter-op gap residual living INSIDE the collective event pairs.

## (c) Fix design (src/ untouched — sketch only)

Two staged fixes; FIX-A is small, env-gated both directions, and correctness-preserving;
FIX-B is the full-class fix designed per the W4-CURE bounds (doc docs/amd/, commit
eb365119f) and lands only after FIX-A's M3 fields confirm the split.

### FIX-A — loop-top deferred consume for next-round-consumed argmax calls

Key structural fact that makes it correct: `st.d0 = st.drafts1.slice(0,0,1)` and the chain
`ar_drafts[step]` alias `drafts1` (round_state.cpp:1328) — the d0 and chain-head argmax
outputs are consumed only by NEXT round's `speculative_prepare_verify_inputs`, which is
enqueued after the round top. So their per-call drains can be deferred to a
**loop-top consume point that runs BEFORE any consumer is enqueued** — retry-before-
consumer is preserved, the lag bound becomes one round (~100 ms) vs the K=16 retry budget
(~1.3 s worst-wait platform re-arm, one_shot_allreduce.cu:763-770), and K-exhaustion still
dies loud (`_exit(70)`, no silent failover). Calls whose output is consumed in-span keep
the in-loop drain (verify ar_argmax → accept; in-forward ARs → next op of the same
forward).

### FIX-B — single-drain round (design, staged)

The remaining 5 drains (verify ar_argmax, 2 align ARs, 2 chain fwd ARs) are mid-span:
their outputs feed the very next kernel, so deferral alone is INCORRECT there. The
class-level fix is to stop host-pacing those spans at all:

- Span-graph capture (CUDA/HIP graphs) of the two T=1 spans — [align → select → propose →
  chain] is data-dependent only through `next_F` (host int from `a`) for the Envelope
  args (:3643) and `kvarn_rewind(next_F)`; pass `next_F` as a DEVICE scalar read from the
  accept output (the kvarn rewind + envelope sites take a device-pointer overload) and the
  whole post-accept span captures once per (rk) shape. The verify span [prep → accept+D2H]
  captures per (rk) outright.
- The one-shot flag/payload protocol is already device-side (kernels publish + poll
  host-mapped flags) — a graph replay needs NO host between collectives; status consume
  moves to the round's accept sync (which already exists), with a BOUNDED span-retry:
  a NAK at the boundary consume replays the span graph (greedy + pre-commit ⇒ idempotent),
  K=16, then loud `_exit(70)`. This is exactly the W4-CURE B2 per-collective host-deadline
  shape lifted to span granularity; B3 watchdog unchanged.
- VRAM law: graph pools are MEASURED at boot (live cudaMemGetInfo + actual bytes), no new
  refusal constants; the anti-resurrection diff-gate cells cover tp2_budget.h/tp_engine.

Expected (FIX-A + FIX-B): the 16.3 draft-side class → **~3-4 ms/round** (true T=1 device
work: weight pass + kvarn attend + handshake), round 117.41 → **~104-106 ms**, count600
conc=1 wall −10-12% at unchanged greedy output.

## (e) HONESTY BLOCK — what breaks if I'm wrong

1. **If M2 shows book ≥ 15 ms:** my code-price missed a live arm. Named candidates, in
   order: (a) an env I read as OFF is ON in the window posture — conf_gate
   (NINFER_MTP_CONF_TAU) arms the double barrier INSIDE book (:3284/:3342), and its wait
   absorbs inter-rank host skew at world=4, which is unbounded by anything in book;
   (b) stdout stalls: book contains collect()'s printf+fflush per round per rank
   (verify_tail_trace.h:252-262) — if serve stdout is a slow pipe (not the runbook's
   file redirect), fflush blocks ms-class INSIDE book; the tracer would be measuring
   itself. Either way the fix is NOT in this doc — the check in (d)-1 fires first.
2. **If the draft-side 16.3 survives FIX-A/FIX-B:** the drains were not the cost; the real
   cost is then in-kernel spin-poll peer-wait (kFlagTimeoutPolls) or true T=1 device work
   (weight-pass + kvarn attend at 10k context). The M2 field split (chain_fwd vs
   chain_head; align vs its Σ-kernel residual) names it BEFORE the next patch — no patch
   ships before its decisive measurement.
3. **W4 hazard is real:** FIX-A widens the collective lag window by design; the K=16
   bound, the B2 host deadline, and the census arm are what keep it loud-not-silent. If a
   desync appears in the window, the env toggle (default-off arm) reverts to the exact
   shipped behavior byte-identically.
4. **Throughput honesty:** FIX-A alone is ~2-3% wall — under the noise floor of a single
   count600 leg unless paired leg discipline is used; it must not be claimed as the 16 ms
   fix. Only FIX-B targets the full class, and only after FIX-A's fields confirm the
   split.
5. **Fix-touches-the-wedge-class:** any change to one-shot collectives lands with the
   W4-CURE bounds reviewed in the same change; the RED/GREEN cells above are the closure
   law's price of admission.
